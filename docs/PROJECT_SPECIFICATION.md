## 1. What it is
A read-only After Effects script that scans the project's file references for non-ASCII (Japanese/CJK) path problems and returns SAFE / WARN / BLOCKED per path with plain guidance. It never relinks, renames, converts expressions or edits the project (the sheet marks those as occupied/out of scope).

## 2. Pain it targets (from the sheet; sources NOT re-checked by me)
- AE 26.5 SMB / non-ASCII path failure reproduced by Adobe engineering and ticketed (sheet, cycle 2026-09-23).
- Native-JP reports of Unicode/encoding breakage with some plug-ins (blank parameter names, expression breakage).
- Competitor in the sheet: ExpressionUniversalizer 4 ($49.99) occupies expression conversion — so we stay on diagnosis only.

## 3. Proposed MVP (bounded beta, same standard as the other two)
For every footage/file reference in the project, plus the project file path and render-queue output paths:
1. **Non-ASCII detection:** lists characters outside ASCII and which script class (hiragana, katakana, kanji, other).
2. **Normalization form hint:** flags combining marks (e.g. U+3099/U+309A, U+0300–U+036F), which indicate NFD-style names. ExtendScript has no normalize function, so this is a heuristic, not proof.
3. **Location class:** local / UNC network / cloud-synced / mounted volume (reuses the Write Sentinel's classifier).
4. **Round-trip check:** can the file be found again via its stored path (`File.exists`)? A mismatch is the strongest signal.
5. **Windows path length:** warn above 240 characters, block above 259 (MAX_PATH, unless long paths are enabled — unverified).
6. **Verdict per path + overall:** SAFE / WARN / BLOCKED; "network + non-ASCII" is WARN at minimum (the failure class in the sheet).
7. Output: dialog summary + ExtendScript console JSON, same as the Write Sentinel (no file writes in v0).

Out of scope: relinking, renaming, expression conversion, plug-in localization matrices, Creative Cloud locale inventory (that is idea 23-B).

## 4. Open questions (UNVERIFIED)
- Whether AE exposes the stored path in a way that differs from `File.fsName` (e.g. normalized vs as-stored). Needs a native check with an NFD-named file.
- Whether `File.exists` correctly fails for the NFD/NFC mismatch on Windows NTFS (Windows is mostly normalization-insensitive, so the real failures are probably macOS and network shares; I can't test those).
- Whether a script can read missing-file state without triggering a relink prompt.
